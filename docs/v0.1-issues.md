# v0.1 GitHub issue breakdown

## Milestone

**Title:** `v0.1 - Planning Foundation`

**Release target:** `v0.1.0` (no date committed)

**Goal:** I can create and save a Program Plan.

**Completion:** A user builds a small plan manually, closes Planacity, reopens the
project, and continues editing without losing information.

The v0.1 milestone is active on GitHub. V01-02 is tracked in [issue #2](https://github.com/tidus747/planacity/issues/2)
and V01-03 in [issue #3](https://github.com/tidus747/planacity/issues/3). V01-04 is
[issue #6](https://github.com/tidus747/planacity/issues/6) and V01-05 is
[issue #7](https://github.com/tidus747/planacity/issues/7). V01-06 through V01-11
are tracked in issues #13 through #18. `V01-*` identifiers are local roadmap references, not GitHub
issue numbers. Completed implementations below remain pending review until merged.

Use only the labels needed now: `type:feature`, `type:docs`, `area:ui`, and
`area:domain`. Add other labels when useful; do not create future-area labels yet.

## V01-01 - Bootstrap the desktop shell and developer checks

**Labels:** `type:feature`, `area:ui`

Establish a runnable application and a short, repeatable contributor workflow.

- [ ] Install from `pyproject.toml` into a clean Python 3.11+ environment.
- [ ] Launch through `python -m planacity` and the installed `planacity` command.
- [ ] Show sidebar navigation for Overview, Plan, People, and an informational
  Import placeholder with clear development-preview wording; exit cleanly.
- [ ] Offer light/dark appearance from the sidebar and View menu, restoring the
  local preference on restart without affecting page selection or panel sizes.
- [ ] Keep domain/planning/persistence boundaries separate from Qt presentation.
- [ ] Run Ruff, formatting checks, mypy, pytest, and a package build in CI.
- [ ] Document setup and include an offscreen startup/navigation smoke test.

**Validation:** Local checks plus a green first GitHub CI run on Windows and Linux.
The skeleton supplies the implementation; do not imply the full milestone is done.

## V01-02 - Model ProgramPlan and a flexible PlanningHorizon

**Labels:** `type:feature`, `area:domain`

Create plain typed Python entities for a named plan, description, stable identity,
and date-based planning horizon. Choose a single canonical ID representation.

- [x] Accept arbitrary inclusive start/end dates, including same-day horizons.
- [x] Reject blank names and reversed horizons with actionable errors.
- [x] Create independent plans without shared mutable collections.
- [x] Document identity and date conventions in `docs/domain-model.md`.

**Validation:** Unit tests for normal, same-day, cross-year, and invalid ranges,
blank names, and independent instances. No Qt import or future entities.

## V01-03 - Implement Epic, Task, and Subtask hierarchy

**Labels:** `type:feature`, `area:domain`

Add WorkItem identities, titles, types, explicit parent references, and domain
operations for adding, renaming, reparenting, and removing work.

- [x] Support root Epics, Tasks under Epics, and Subtasks under Tasks.
- [x] Permit standalone Tasks; require a Task parent for each Subtask.
- [x] Reject unknown parents, invalid type combinations, duplicate IDs, and cycles.
- [x] Keep relationships and WorkGroups separate from parentage.
- [x] Define deletion behavior explicitly; never silently lose descendants.
- [x] Preserve sibling order and validate before applying mutations.

**Validation:** Unit tests for nested work, reparenting, deletion, missing parents,
cycles, and failed edits leaving the plan unchanged. Document hierarchy rules.

## V01-04 - Add people, estimates, and planned dates

**Labels:** `type:feature`, `area:domain`

Add Person records and optional estimates in hours and start/end dates on work.

- [x] Create, rename, and remove people using stable identities.
- [x] Distinguish an unknown estimate from zero hours; accept fractional hours.
- [x] Reject negative and non-finite estimates and reversed work date ranges.
- [x] Allow incomplete planning data, such as unset estimates and dates.
- [x] Preserve out-of-horizon dates and expose findings to the editor; never clamp them.
- [x] Do not add `WorkItem.owner`; v0.1 people are a roster. If assignment scope
  changes, design it as a separate multi-person Allocation entity first.

**Validation:** Unit tests for fractional/zero/missing estimates, invalid numbers,
partial dates, reversed dates, and people lifecycle. No availability or load math.

## V01-05 - Add WorkGroups and basic relationships

**Labels:** `type:feature`, `area:domain`

Organize work independently from hierarchy and record simple work relationships.

- [x] Create, rename, and remove WorkGroups; a group may contain multiple Epics.
- [x] Removing a group preserves its work and explicitly removes memberships.
- [x] Support `related_to`, `depends_on`, and `blocks` between existing work IDs.
- [x] Reject dangling links, self-links, and duplicates; document link direction.
- [x] Work removal handles affected relationships explicitly without dangling IDs.
- [x] Record dependencies without automatically changing dates or estimates.

**Validation:** Unit tests for multi-Epic membership, links, duplicate/self/missing
endpoints, and safe removal. Automatic scheduling and dependency-risk analysis are excluded.

## V01-06 - Build the editable hierarchical Plan view

**Labels:** `type:feature`, `area:ui`

Connect a `QTreeView` and `QAbstractItemModel` to canonical WorkItems.

- [x] Display and expand/collapse Epic/Task/Subtask hierarchy.
- [x] Add, rename, reparent, and delete work through domain operations.
- [x] Support keyboard navigation and inline title editing.
- [x] Show validation errors without losing the current selection or edit context.
- [x] Confirm operations that remove descendants; cancellation preserves the plan.
- [x] Notify Qt correctly when rows change; do not duplicate domain state in widgets.

**Validation:** Selective model tests for indexes/parents, row insertion/removal,
and rejected edits; manual keyboard check. Include a screenshot in the PR.
Bulk paste, advanced filters, and configurable columns are not required for v0.1.

## V01-07 - Expose people, dates, estimates, groups, and relationships

**Labels:** `type:feature`, `area:ui`

Complete the first planning surface using small dialogs or inline editors.

- [x] Edit a people roster and work estimates/dates through the canonical model.
- [x] Show hour units and unambiguous dates; distinguish unset values from zero.
- [x] Manage WorkGroups and link/unlink relationships without changing parentage.
- [x] Display actionable errors and out-of-horizon conditions; preserve invalid
  edits for correction without committing invalid data.
- [x] Expose the same values consistently after switching views.

**Validation:** Domain tests remain the source of business-rule coverage; add
selective Qt adapter tests and manually check keyboard editing and cancellation.
No capacity charts, workload scores, or automatic assignment.

## V01-08 - Persist complete plans in a versioned SQLite project

**Labels:** `type:feature`

Use standard-library SQLite for one local project file. Document the format in
`docs/project-file-format.md` before treating it as a compatibility contract.

- [x] Round-trip metadata, horizon, work/order/hierarchy, people, estimates, dates,
  groups/memberships, and relationships without loss of identity or precision.
- [x] Store a schema version and reject unsupported newer files with a clear error.
- [x] Validate loaded data before exposing it as an editable plan.
- [x] Save transactionally; a failed save preserves the previously saved project.
- [x] Report corrupt files and file-access failures without replacing in-memory data.
- [x] Do not add an ORM or a migration framework for hypothetical schemas.

**Validation:** Temporary-file tests for complete round trips, Unicode, empty and
incomplete plans, corrupt/foreign/newer files, and rollback on failed saves.

## V01-09 - Add New, Open, Save, and Save As workflows

**Labels:** `type:feature`, `area:ui`

Wire domain creation and SQLite persistence into the desktop application.

- [x] New collects a name, description, and valid horizon; metadata remains editable.
- [x] Open replaces the current plan only after successful loading and validation.
- [x] Save and Save As support normal keyboard shortcuts and update the project path.
- [x] Display unsaved changes and prompt to save/discard/cancel on New, Open, and Exit.
- [x] Cancelling a dialog or failing a save preserves data and unsaved status.
- [x] Confirm overwrites; report the affected file and a useful recovery action.

**Validation:** Tests for document state transitions and mocked file-dialog/error
paths; manual Windows edit/save/close/reopen check. No recent-files framework needed.

## V01-10 - Export and restore JSON plan backups

**Labels:** `type:feature`

Provide a portable, versioned JSON backup through the same canonical model.

- [x] Export all supported fields with explicit schema version, IDs, and ISO dates.
- [x] Restore a valid backup as an unsaved plan after validating the complete file.
- [x] Reject malformed, unsupported, or incomplete structural data with clear errors.
- [x] Invalid restore leaves the current plan intact; valid restore follows the
  same unsaved-change prompt as Open.
- [x] Never silently ignore unknown fields or overwrite the active SQLite project.
- [x] Document the backup workflow and ensure interrupted export cannot destroy
  an existing backup (write to a sibling temporary file, then replace).

**Validation:** JSON-to-model round trips including Unicode and optional values;
malformed/newer data and export failure tests. This is not a Jira CSV exporter.
